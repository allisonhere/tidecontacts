# TideContacts graphical feature parity

Status after Phase 4C implementation. Baseline: Community `feat/phase3d-automation-host` and the local private Professional `feat/phase3d` checkout. Phase 4A produced a fictional static design study and a Qt revenue prototype. Neither is a graphical CRM. No Phase 4B application adapter, Svelte frontend, installable desktop application, or TideGUI dependency was found before Phase 4C. Phase 4C added the loopback adapter (`internal/webapp`, `cmd/tidecontacts-web`), a Svelte client (`web/`) and a Qt Quick Community client (`desktop/`); the Web and Desktop cells below describe what those now provide in these local branches or the reachable public TideContacts heads. The private remote could not be refreshed; local checked-out code is the Professional evidence. No earlier graphical parity is assumed.

**Complete** means that the specified capability has a working backend and graphical workflow. **Partially implemented** means that the row contains named working and missing parts. **UI missing** and **Backend ready** mean a working service exists but neither proves a graphical route. **Not implemented** means the required end-to-end machinery was absent. **Deferred** is intentionally outside the first increment; **Blocked** requires an inaccessible dependency or external decision. TUI/CLI/MCP columns describe actual established access, not promises of parity.

## Implementation order

1. Establish the explicitly authorized, versioned graphical adapter on existing data and a real browser plus desktop launch path. First prove contact → dossier → related record → back and revision-safe writes.
2. Extend the same transport with daily operations. Keep typed server validation and app-owned IDs; never share script execution or file paths with browser clients.
3. Bridge each approved Professional operation by capability, explicitly separating passive read projections, ordinary edits, and consequential approvals. Keep extension code private.
4. Fill productivity/platform gaps only where the UI can drive a verified operation. Record real screenshot and workflow evidence before calling a row complete.

## Phase 4D plan (open items after Phase 4C)

Recorded at the end of Phase 4C; none of these is implemented.

1. Browser: saved views and in-app navigation history, onboarding, integration settings, Inbox/Radar and transfer screens.

4. A screen-reader, keyboard-only and contrast audit of both clients, and a performance measurement against the 10,000-record fixtures.
5. Update the reusable modern-gui skill with the pane, settings and capture patterns used here.
